# DeltaFront: external services and the account backend

DeltaFront is a fork of OpenFront. OpenFront runs a closed-source account API (a Cloudflare Worker at `api.<DOMAIN>`) that this repository does not contain. Everything below that needs it is **off by default** in DeltaFront.

The switches live in [`packages/shared/src/AccountFeatures.ts`](../packages/shared/src/AccountFeatures.ts) (`ACCOUNT_FEATURES`), read by both the client and the server. Product settings (links, Steam, ads, tutorial video) live in [`src/client/Branding.ts`](../src/client/Branding.ts).

## What works with no backend

Solo play, the tutorial, private lobbies (create and join, two or more players), the scheduled public lobbies on a local server, settings, help, news (bundled `resources/news.json`), and the whole simulation.

Other server calls to the API, all failing open or being skipped without a backend: `POST /join_verify` (Turnstile + name screening), `POST/GET /game/:id` (game archive; skipped unless a flag is on), `POST /cluster/checkin` (deployed hosts only), a lobby-coordinator websocket (only with `LOBBY_COORDINATOR=api`).

### Newer flags, and turning flags on (`DF_ACCOUNT_FEATURES`)

DeltaFront's own account backend ([`src/account-api`](../src/account-api), planned in [DeltaFrontAccountsPlan.md](DeltaFrontAccountsPlan.md)) adds five flags. They exist from milestone M0 but **nothing reads them yet**; each gets its first use in the milestone that owns the feature, and until then turning one on changes nothing.

| Flag             | Will hide when off                                                                                     | Wired in |
| ---------------- | ------------------------------------------------------------------------------------------------------ | -------- |
| `payments`       | Real money and the premium currency: currency packs, subscriptions, checkout, creator codes, donations | M4       |
| `friends`        | Friends list and requests                                                                              | M1       |
| `progression`    | XP, levels, prestige, reward claims, achievements                                                      | M1       |
| `tribes`         | Custom tribe names and the tribe leaderboard                                                           | M4       |
| `trustedLobbies` | The trusted-accounts-only public lobby rotation                                                        | M1       |

Every flag is off unless `DF_ACCOUNT_FEATURES` names it. The value is a comma-separated list, e.g. `DF_ACCOUNT_FEATURES=accounts,leaderboards`:

- unset or empty means everything off (what ships);
- names must match exactly (case-sensitive); an unknown name enables nothing and is reported (a warning, but the account API refuses to start outside dev);
- there is no wildcard and no way to switch a flag off, only on;
- the client reads it **at build time** (Vite) and the game server and account API read it **at startup**, so a build and the servers it talks to must be given the same value. Put it in the same `.env` (or deployment environment) for all of them. Under `vitest` it is always empty, so a variable in your shell cannot change the test suite.

Enabling a flag in production is the public launch of that feature, so it waits for the milestone's acceptance criteria, and for the account launch also the final Terms of Service and Privacy Policy (the pages in `resources/public/` are labelled placeholders).

### The account API (`src/account-api`)

A separate Node service that answers the `api.<DOMAIN>` contracts the client and game server already speak. **Milestone M1 (core sign-in, production admission, server discovery)** **milestone M2 (profiles, persistent stats, Credits earning)**, **milestone M3 (the basic player leaderboard)** **milestone M4 (the cosmetic catalog and inventory)**, **milestone M5 (the Credits store)** and **milestone M6 (clans)** are implemented; ranked ladders and email sign-in are later milestones and are not served.

What it serves follows the feature flags, so nothing is exposed for a feature that is off:

| Needs                     | Endpoints                                                                                                                                                                                                                                                                                                                                                                                                                             |
| ------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| always                    | `GET /health`                                                                                                                                                                                                                                                                                                                                                                                                                         |
| `accounts`                | `POST /auth/refresh` (also mints guests), `POST /auth/logout`, `POST /auth/revoke`, `GET /auth/login/{discord,google}`, `GET /auth/callback/{discord,google}`, `GET /auth/link/google`, `GET /users/@me` (with the Credits balance), `PUT /users/@me/username`, `DELETE /users/@me`, `GET /player/:publicId`, `GET /public/player/:publicId`, `GET /public/player/:publicId/games`, `GET /.well-known/jwks.json`, `POST /join_verify` |
| `inventory`               | `GET /cosmetics.json` (the DeltaFront catalog), `GET /cosmetics/assets/:file`, `GET /reserved_clan_tags` and `POST /custom_tribes` (game server only, `x-api-key`; both empty until clans / never for tribes), and `flares` in `GET /users/@me`. Also served for `store` or `clans`, which read the same catalog.                                                                                                                     |
| `clans` (with `accounts`) | The clan API the client already speaks (`GET/POST /clans`, `/clans/:tag` and its `members`, `requests`, `bans`, `games`, `join`, `leave`, `kick`, `promote`, `demote`, `transfer`, `ban`, `unban`; `PATCH` and `DELETE /clans/:tag`), `GET /public/clan/:tag/exists`, `GET /public/clans/leaderboard`, and `clans` / `clanRequests` in `GET /users/@me` and the public profile. Donations are not served.                             |
| `store` (with `accounts`) | `POST /shop/purchase` (spend Credits on a catalog item). Bundles (`/shop/purchase/pack`), checkout, subscriptions and the premium currency are not routed.                                                                                                                                                                                                                                                                            |
| `leaderboards`            | `GET /leaderboard/players?page=N&period=all\|30d` (the basic player board; also starts the 5-minute rebuild job)                                                                                                                                                                                                                                                                                                                      |
| any feature flag          | `POST /cluster/checkin`, `GET /cluster.json?site=`, `POST /game/:id` (a game server's finished game: stored, then turned into stats and Credits), `GET /game/:id` (replays), `GET /news.json`, `GET /streams.json`                                                                                                                                                                                                                    |

**Inventory (M4).** The catalog is data: [`src/account-api/catalog/cosmetics.json`](../src/account-api/catalog/cosmetics.json) (the client's own `CosmeticsSchema` shape plus `defaultFlares`, the free items every account owns) and the images in `catalog/assets/`. It is validated strictly when the API starts (duplicate or mismatched ids, missing or path-like assets, any `priceHard` / Stripe `product` / bundle / skin / crown section, an effect the client would silently drop, an unknown default) and a mistake stops the boot. Adding an item is an entry plus, for a flag, an image. Ownership is the `user_flares` table, reported as `player.flares` in `/users/@me` (the free items plus what the account holds, filtered to items the catalog defines); only `npm run admin -- item:grant|item:revoke|item:list` writes it, and no HTTP route can. Equipping stays client-side (the existing design): the selection is stored per account in the browser and sent with the join, and the game server refuses a join that names a cosmetic the account does not own. The `inventory` flag shows the INVENTORY page (it needs `accounts`); the Store page and the Store button inside the inventory belong to `store` (M5) and stay hidden.

**Store (M5).** Prices are `priceSoft` entries in the catalog (Credits, positive whole numbers; nothing in client code). `POST /shop/purchase` takes the existing client contract (`cosmeticType`, `cosmeticName`, `currencyType`, `colorPaletteName`) and reads nothing else: the flare and price come from the server's catalog, only registered accounts may buy (a guest gets `403 LOGIN_REQUIRED`), and `currencyType` must be `"soft"`. In one transaction it locks the wallet, refuses an item already held or free by default (`409`) or a short balance (`400 Insufficient balance`), then debits the price, writes the `purchases` row and a `purchase` ledger row, and grants the flare; any failure rolls all of it back. Admin: `wallet:show`, `wallet:grant <publicId> <credits> --reason <text>` and `wallet:revoke <publicId> <credits> --reason <text> --yes` (the only other way a balance moves besides game rewards and purchases; a deduction larger than the balance is refused, and each change is audited with its ledger row).

**Clans (M6).** Rules live in [`domain/clans.ts`](../src/account-api/domain/clans.ts) (the permission table `can()`, `checkCreateEligibility`, name, tag, description and Discord-link validation) and every change is a function in [`domain/clanOps.ts`](../src/account-api/domain/clanOps.ts): one transaction that locks the clan's row, re-reads the caller's role inside it and asks `can()`. The browser sends a tag in the path and a `targetPublicId`, never a role. Creating needs a registered, unbanned account at least 3 days old with 10 completed games (`CLAN_RULES`); one clan per account is `UNIQUE clan_members(user_id)`, so two racing joins cannot both succeed, and one leader per clan is a partial unique index. A leader with other members cannot leave (`TRANSFER_REQUIRED`); a sole member leaving disbands the clan, which holds its tag for 90 days. `clans/reserved.json` lists the tags and name imitations nobody may take (staff, system, DeltaFront); `GET /reserved_clan_tags` serves it plus every live and held tag to the game server, which also asks `GET /reserved_clan_tags/:tag` for a tag a player wears but does not own, so a clan created since its last refresh is protected at once. A game player's row is tied to a clan only when they were a member wearing that clan's tag; the clan board (`/public/clans/leaderboard`) is computed from those rows for the last 30 days. Admin: `clan:list`, `clan:show`, `clan:rename`, `clan:transfer`, `clan:member-remove`, `clan:remove` (reason required; all but `clan:rename` need `--yes`; each writes `admin_audit_log` in the same transaction). No migration: the clan tables came with `0001`.

**Leaderboard (M3).** `leaderboard_players` is rebuilt every 5 minutes from the stored counted games (one transaction, an advisory lock so a second instance skips) and each request reads one page of it: 50 rows, at most 20 pages, with a `400 Page must be between 1 and N` past the end, which is what the client already treats as the end of a board. A player needs 10 counted public games in the period; order is wins, win rate, games, public id; ranks are competition ranks on (wins, win rate). Flagged, banned, deleted and deletion-queued accounts are filtered out at read time as well as at rebuild, so they vanish at once. Run migrations (`0002`) before starting.

**Stats and Credits (M2).** Only a game server can report a game: `POST /game/:id` needs a server key (`x-api-key`) and refuses any request that carries an `Origin` header, so a browser can neither submit a result nor change a balance. Each record is applied in one transaction and exactly once (repeats and concurrent duplicates change nothing). The rules are in [`domain/stats.ts`](../src/account-api/domain/stats.ts) (what counts, what a completed game is) and [`domain/economy.ts`](../src/account-api/domain/economy.ts) (the only code that credits a wallet); the numbers (100 per completed game, 250 more for a win, 1,000 a day) are in `constants.ts`. Credits ride in the `soft` slot of `/users/@me`'s `currency`; `hard` is always 0. Two background jobs run in the service: deletions requested through `DELETE /users/@me` are carried out after 24 hours, and idle guests with nothing to keep are removed after 30 days.

```bash
npm run account-api:migrate           # apply pending migrations (needs DATABASE_URL)
npm run account-api:migrate -- status # what is applied and what is pending
npm run start:account-api             # start the service
npm run admin -- help                 # admin commands (users, bans, items, server keys, server states)
npm run test:account-api              # database tests; needs DATABASE_URL_TEST

# Local development with accounts on (guest + Discord + Google), needs PostgreSQL:
export DATABASE_URL=postgres://user:password@localhost:5432/deltafront_dev
npm run account-api:dev-setup # migrate, and register the dev game-server key
npm run dev:accounts          # client + game server + account API (DF_ACCOUNT_FEATURES=accounts,leaderboards)
```

- It needs **PostgreSQL**. There is no fallback database, and the service refuses to start if the database is unreachable or has pending migrations (it never migrates implicitly: run the migrate command as a deploy step first).
- Configuration is read from the environment (a `.env` file works). See [`example.env`](../example.env) for every variable; nothing secret is committed. `GAME_ENV` has no default, and outside `dev` the service fails at startup, listing every problem, if something it needs is missing: the domain and origins, and, when `accounts` is enabled, the signing key, the Turnstile secret and Discord and Google credentials.
- **Signing key.** Access tokens are Ed25519 JWTs. Generate the key once with `openssl genpkey -algorithm ed25519 -out jwt.pem` (keep it out of the repo, mode 600) and point `JWT_PRIVATE_KEY_PATH` at it. Only the public half is published, at `/.well-known/jwks.json`. In `dev` with no key configured the service creates one in `.account-api-dev/` (gitignored) and reuses it.
- **Provider apps.** Register `https://api.<DOMAIN>/auth/callback/discord` (Discord, scopes `identify email`) and `https://api.<DOMAIN>/auth/callback/google` (Google, scopes `openid email profile`) as the redirect URIs; locally that is `http://localhost:8787/auth/callback/...`.
- **Game servers authenticate with `API_KEY`.** Create one per server with `npm run admin -- server:key:create <name>` (shown once; only its hash is stored) and give it to the game server as `API_KEY`. With any account feature on, the game server refuses to start without it, and refuses the dev placeholder key outside dev.
- **Server discovery.** A deployed game server needs `SUBDOMAIN`/`GAME_HOST`, `INSTANCE_LETTER` and a commit-shaped `GIT_COMMIT` to check in (the local dev build uses `DEV`, so a dev server does not register and schedules its own lobbies). New servers start `open`; `npm run admin -- server:state <site> <letter> open|draining|fenced --yes` is the operator's switch.
- **Behind a reverse proxy** set `TRUST_PROXY_HOPS` (nginx = 1), or every player appears to come from the proxy's address and shares one rate limit.
- The owner-defined numbers (Credits rewards, the daily cap, clan creation rules) live in [`src/account-api/domain/constants.ts`](../src/account-api/domain/constants.ts) and nowhere else.
- Migrations are forward-only files in `src/account-api/migrations/`. Applied files are never edited (their checksums are verified); change the schema with a new file.

## Production deployment notes

A server run with `GAME_ENV=prod` (or any non-dev environment) behaves differently from local dev:

1. **Who may join.** `verifyClientToken` rejects anonymous player IDs outside dev ("persistent ID not allowed in production"), so every player needs a JWT from the account API (`/.well-known/jwks.json`). A guest is a real account the API created, not an arbitrary client id. Every first join also needs a Cloudflare Turnstile token, which the API verifies (`POST /join_verify`).
2. **Public lobbies on a deployed host.** A host that has a `SUBDOMAIN` registers with the API (`POST /cluster/checkin`) and schedules nothing until the API answers `open`. A server the operator has set to `draining` or `fenced` stops adding lobbies.
3. **Turning it on is the public launch.** Nothing here is enabled in production until `DF_ACCOUNT_FEATURES` names `accounts`, which also waits for the final Terms of Service and Privacy Policy (see `docs/DeltaFrontAccountsPlan.md`, M7). The Docker build does not pass `DF_ACCOUNT_FEATURES` to the client build yet, so production client bundles stay feature-free until the deploy pipeline does.
